# Payment and dispensing transaction abort review

Engineering batch, 19 October 2026. Baseline: `fd27cf441a1883cb4a676c3f52046f5fca83f73c`; live application source remains `89e693df430571b9371cefad7db1e750ae41fe30` (1.6.2). This batch is not a production release or clinical/regulatory approval.

## Problem and correction

The two high-priority entries in `releases/2026-10-17-transaction-review-backlog.json` identified payment and dispensing loops that recognized Prisma P2034/P2002 but omitted P2010 wrapping PostgreSQL 40001 or 40P01. They now use the existing structured conflict classifier for known-aborted transactions. P2002 remains a separate, existing reconciliation path. All branches share the original maximum of three complete transactions, with unchanged Serializable isolation and immediate retry timing. There is no nested helper, expanded budget, message-text inference, or automatic replay after an unknown/network outcome.

Every retry reruns the original callback. Payments reread facility-scoped replay, invoice, legacy reference, cash shift and patient balance after insurer allocation; receipt sequence, payment, receipt, invoice/visit/queue state, audit and replay response remain atomic. Dispensing rereads actor-bound request evidence, scoped order and visit, remaining prescription, active/equivalent formulary item, frozen-store status, valid unexpired stock, FEFO/substitution reasons and invoice state. Stock, trace items, journal, charges, prescription, handoff and audits remain atomic. No external payment/provider or dispensing integration was introduced.

Authorization and MFA still run before the transaction; this patch does not add per-attempt session/role revocation checks. Payment replay retains its existing facility/invoice/fingerprint contract, which is not actor-bound. Dispensing retains its actor/facility/order/fingerprint contract. Existing PAYMENT_RECEIVED and MEDICATION_* success events omit sessionId; the DISPENSING_REQUEST_RECORDED receipt does retain it. This attribution backlog is explicit rather than silently counted as resolved.

## Verification and limits

- Twenty-eight new route regressions cover both raw codes, mixed P2002/serialization budgets, changed winners, original payload identity, closed visits, cash-shift and balance revalidation, current authorization, facility scope, private/no-store errors and ambiguous failures. Correctly generated-client baseline: 13 failures/41 passes. Corrected focused suite: 79 passes in three files; complete suite: 1,196 passes in 124 files. Types, production build, 55 migration checks and zero production dependency vulnerabilities passed.
- The disposable native PostgreSQL fixture first rejects the final business audit with P0001. Exactly one rejection is observed and complete before/after snapshots of 19 affected tables, including audit events/head, must match. This proves actual rollback, rather than only modeled callback behavior.
- For the successful retry, a separate fixture transaction locks the facility audit head. The harness observes the application's raw SELECT FOR UPDATE waiting, commits a no-op row-version update and requires the original HTTP request to succeed. Retained server logs show 40001 at that raw SELECT. Durable checks require one payment/receipt/replay/counter increment or one dispensation/stock movement/charge/balanced journal, correct actor/facility linkage and the dispensing session receipt. Full fixture export additionally verifies the audit chain.
- This is controlled contention on one synthetic facility, not a load test or deadlock reproduction. 40P01 is covered by route/classifier unit tests. PGlite's default fixture path retains explicitly injected SQL-abort checks and does not claim native lock contention.
- The initial unit invocation ran before dependency generation finished (49 failures/5 passes); its log is retained, not used as the regression baseline. Type checking also caught two test-union access errors, corrected before the successful check. The first native setup used Windows WIN1252 and failed bootstrap on Unicode; a fresh UTF-8 database resolved it. The second native harness failed to observe a lock because PostgreSQL cached its activity snapshot within the blocking transaction. Following the primary [PostgreSQL activity snapshot documentation](https://www.postgresql.org/docs/current/monitoring-stats.html), clearing that snapshot before each poll fixed the observation without changing runtime code, timeout, assertions or retries. Both failed databases/logs are retained.

Final browser, standalone-native, exact source and hosted-CI results are recorded in the batch evidence and workflow log. Local application build: `HmiX6cGJtNRpR9d6U8_xY`; final fixture-only edits followed that build and do not modify compiled application code. Production version/build/source identifiers were not reassigned to this candidate.
