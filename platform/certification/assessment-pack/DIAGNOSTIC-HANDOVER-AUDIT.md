## Findings and current boundary

The existing workflow provides self-acceptance of responsibility and explicit acknowledgement of a verified report. A covering clinician can take responsibility by submitting `CLAIM` against the latest event. It does **not** provide an offer addressed to a nominated receiver, pending acceptance, decline, withdrawal, escalation or an acknowledgement addendum. These are known unfinished capabilities, not newly implemented features.

| Area | Verified current behavior | Remaining engineering work |
| --- | --- | --- |
| Acceptance | Both `encounter.write` and `clinical.results.read` are required. `CLAIM` records the authenticated actor, not a client-supplied owner. A facility-scoped order lock and expected event ID serialize responsibility changes. | Separate an offer from receiver acceptance. A new offer must not silently replace the current accepted owner. Define an explicit initial-unowned and inactive-owner recovery path. |
| Inactive owner | Shared authentication refuses DISABLED and LOCKED accounts, including otherwise verified MFA sessions. | `diagnosticEventSelect` returns actor ID/name, but no current account status or eligibility. The UI therefore cannot distinguish an inactive historical owner from an active one; do not claim this warning exists. Preserve the historical actor while showing current eligibility separately. |
| Handover history | New responsibility events append a sequence. Mutation audit records actor, facility, session and prior event fingerprint. SQL prohibits updating/deleting review events. | There is no offerer/receiver pair or offer state. A self-claim note is not evidence that the prior clinician offered or agreed to transfer responsibility. |
| Released report | Acknowledgement requires current ownership, exact result ID, verification timestamp and explicit attestation. The selection filters for verified results; laboratory and imaging paths are supported. | History rendering omits the event's result ID and original verification timestamp, although the API returns them. Add these to saved/printed acknowledgement fields without confusing the current report with the historical acknowledged version. |
| Replay and failure | Exact retries confirm the historical action even after reassignment, acknowledgement or cancellation. Changed actor/order/payload conflicts; replay must pass current authorization and audit. The browser refreshes current ownership after confirming an old request. | Preserve this historical/current distinction in future offer and acceptance responses, especially after an ambiguous network failure. ## Next bounded implementation contract

Implement explicit offered/accepted responsibility as its own versioned batch after the current release. The following is an engineering proposal, not an approved clinical policy:

1. Keep the current accepted owner until an eligible nominated receiver deliberately accepts. Store offerer, receiver, prior owner, order, sequence/revision, server timestamp and reason. Distinguish initial responsibility acceptance from transfer acceptance. Define decline/withdraw/supersede without erasing events.
2. Validate facility, current account status, session/MFA and required role permissions at acceptance. Recheck receiver eligibility at commit rather than trusting a previously displayed chooser. An inactive owner must remain attributable and visibly inactive; a locally authorized covering clinician must have an explicit recovery route.
3. Bind each request UUID to actor, facility, order, offer/revision and payload. Exercise simultaneous accept/decline/withdraw, stale offers, changed receivers, network ambiguity, exact replay and audit failure on native PostgreSQL. Assert one durable responsibility transition, correct audit chain and no cross-facility disclosure. Avoid weakening locks or introducing retries for ambiguous commits.
4. Keep result release, responsibility acceptance, report acknowledgement, critical-result communication and patient contact distinct. Preserve closed-visit review. Decide acknowledgement corrections and new report versions through an append-only design; the current one-acknowledgement index cannot simply be bypassed.
5. Use compact blue-and-white related fields for offer, receiver, reason and status, with the same field order in saved records and print. Show missing/inactive/unaccepted states explicitly. Test desktop/tablet/phone/touch/keyboard, stale refresh, pending actions, lost responses, 50+ history and printing.

Durable offer state would require a reviewed schema change, fresh retained verified backup, controlled migration and final-source release checks. The October 15 backup exception does not apply. Clinical escalation deadlines, emergency coverage policy, external messaging and professional/regulatory acceptance remain separate gates. The existing stock replay, pharmacy clarification and other priorities in the adaptation register remain in the pipeline; this audit does not displace them.
