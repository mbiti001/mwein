## Patterns deliberately not adopted

- The inspected pharmacy finalization method in `PharmacySalesController.cs` updates all non-final items for a patient; Mwein must keep precise order/visit/line/revision boundaries. Positive stock alone is not usable stock: retain store, expiry, quarantine, quantity and allocation checks.
- `PharmacyPrescriptionController.cs` derives quantity from frequency times days without establishing dose quantity and unit conversion. Keep Mwein's explicit verified supply quantity and approved clinical rules. Do not infer Kenya therapeutic equivalence or dosing from this reference.
- The receipt service matches item IDs and clamps negative pending quantities; preserve exact line identity and explicit overreceipt rejection. Separate successful persistence from any later notification failure.
- `InventoryReceiptNumberService.cs` uses a maximum-plus-one pattern. Preserve Mwein's transactional document counters and immutable serial references; do not replace them with an unproven concurrent allocator.
- Transfer receipt takes a client timestamp and uses a visit-only lookup in the inspected path; use server time and independent facility predicates. Pending-transfer retrieval can update expired holds; retain deliberate mutation boundaries.
- Home-medication entry defaults last-taken to today, and some medication components are placeholders. Keep unknown history unknown; file presence is not evidence of a completed workflow.
- The supplied build files describe Angular 7, TypeScript 3.1.6, ASP.NET Core 2.0/.NET Framework 4.6.1 and a Node 10.15.3 watch-build pipeline. The supplied ignore file excludes lockfiles. These are reference architecture details, not Mwein's deployment configuration: preserve the existing stack, committed lockfile, exact-source CI and independent release retests.

## Implementation and release boundary

Each row becomes a bounded implementation batch with an allocated version, negative and positive tests, independent expected stored outcomes, authorization/facility isolation, audit/failure/retry coverage and browser verification. Every available participating agent must test or independently retest the final frozen source before deployment. A database change requires its own fresh retained verified backup and controlled migration; an application-only change requires proof of no database/provisioning changes. One coordinator owns deployment and checks the live baseline before promotion.

Reference source is engineering evidence, not Kenyan legal/clinical approval. The [official DHA HIE go-live process](https://hie-docs.dha.go.ke/docs/goLive) retains separate development testing, UAT, certification and production-credential phases. Existing legal, clinical, security and recovery acceptance gaps remain in the [workflow log](../../WORKFLOW_IMPROVEMENT_LOG.md). No external demo, bundled credentials, database backup or source script was used or executed during this review.
