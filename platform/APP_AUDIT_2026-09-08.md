# Mwein HMIS application audit and remediation status

Audited on 8 September 2026. This is an engineering and product-readiness review of the canonical Next.js/PostgreSQL application in `platform/`; it is not a clinical-safety, penetration-test, privacy, or regulatory certification.

## Remediation update — 14 September 2026

The seven agreed engineering workstreams have been implemented and validated in the repository. The application is substantially safer and more operable, but it is deliberately **not yet cleared for live clinical use**: production readiness now fails closed until the external governance evidence, identity provider, backup target, retention target, and required health-system integrations are supplied.

### Completed engineering work

1. **Role-scoped access and data minimization** — visit and patient APIs now select and return role-appropriate fields, sensitive clinical endpoints have explicit permissions, tenant isolation is exercised in end-to-end tests, and redacted views no longer invent missing clinical or financial data.
2. **Authentication and session hardening** — tenant-aware login, persistent rate limiting, temporary-password replacement, session revocation, idle and absolute expiry, origin checks, security headers, and authentication audit events are in place. Production is gated on a real external identity provider and enforced MFA rather than claiming an in-app substitute.
3. **Tamper-evident audit ledger** — audit events are facility-scoped, sequentially hash-chained, serialized under database locking, protected from update/delete by database triggers, exportable with a digest, and independently verifiable.
4. **Operational readiness** — database migration and bootstrap are separated from build, liveness and fail-closed readiness endpoints are distinct, runtime error reporting is structured, and backup/restore, retention, incident, downtime, and release procedures are documented.
5. **Automated verification** — unit, migration, API end-to-end, and authenticated Playwright suites cover authorization, tenant isolation, password replacement, rate limiting, origin protection, audit verification, readiness gates, core outpatient workflow, admin controls, and responsive navigation.
6. **Governance and integration gates** — nine auditable release gates cover clinical UAT, DPIA, penetration testing, restore evidence, MFA, incident response, terminology validation, audit retention, and DHA integration. Existing external integration holds remain explicit rather than being represented as complete.
7. **Product completeness and performance** — a longitudinal patient problem list was added, consultation workflows can record and resolve problems, and workstation bundles are lazy-loaded to reduce the initial client payload.
8. **Connected-workflow safety pass** — visible queues refresh automatically, triage begins with no prefilled observations and records the minimum presenting concern needed for safe prioritization, system administrators receive clinical access only through an additional operational role, diagnoses must come from a signed validated ICD selection, referral reporting counts actual sent referrals, and pharmacy now distinguishes live-stock loading from no stock while restoring patient-safety context and exact full/partial-supply wording.

## Baseline audit — 8 September 2026

## Executive assessment

The outpatient workflow is technically coherent and materially more mature than a prototype. Registration, appointments, triage, consultation, diagnostics, pharmacy, billing, claims, referrals, stock control, accounting journals, reporting, role-based access and audit events share one facility-scoped data model. Transactions, idempotency keys, immutable clinical subrecords and database constraints are used in the highest-risk write paths.

The current branch is buildable, but it is not ready for live patient use. The largest remaining risks are authentication hardening, independently verifiable audit retention, clinical governance/UAT, live external integrations, and operational production evidence.

## Verification evidence

- `npm test`: 25 test files and 105 tests passed.
- `npm run lint`: strict TypeScript validation passed.
- `npm run db:validate`: Prisma schema validation passed with an isolated validation URL.
- `npm run test:migrations`: all 26 migrations applied in order; required tables, immutable-record triggers, stocktake uniqueness and balanced-journal constraints passed.
- `npm run build`: the Next.js 16 production build completed and generated all application/API routes.
- `npm run test:e2e`: the isolated outpatient journey passed all 19 checks from migration/bootstrap and authentication through registration, triage, structured complaints, diagnosis, referral, prescribing, FEFO dispensing, payment and visit closure.
- Browser smoke check: the public entry page loaded with meaningful content, no framework error overlay and no console warning/error. Authenticated visual testing still requires a usable local PostgreSQL-backed staff session.
- `npm audit --omit=dev`: two moderate findings are reported through `exceljs@4.4.0` → `uuid@8.3.2`. npm's automatic remediation proposes a breaking ExcelJS downgrade and must not be applied without import/export regression testing.

## Strong controls already present

- Every reviewed clinical and operational API route authenticates a staff session and applies a permission check; patient, visit, stock, billing and reporting queries are consistently scoped to the user's facility.
- Clinical, stock, claim and payment writes use database transactions, and replay-prone workflows use idempotency keys.
- Signed encounters are locked; corrections use append-only addenda. Dispensations, referral links/acknowledgements and accounting controls have database-level immutability or balance constraints.
- Pharmacy prevents negative stock, uses FEFO allocation, records justified substitutions/overrides and links stock movements to accounting journals.
- The repository has broad unit/API coverage plus ordered migration verification and an isolated outpatient end-to-end harness.

## Findings and priorities

### P0 — release gates

1. **Authentication is not production-hardened.** Staff login is password-only, there is no MFA/identity-provider integration, failed-login throttling is not implemented in the canonical app, and `Session.lastSeenAt` is not used to enforce an idle timeout. Complete account recovery, forced reset, session revocation and security-event monitoring before live use.
2. **Audit evidence is not independently immutable.** `appendAudit` creates a hash-linked record, but `AuditEvent` has no database mutation-prevention trigger, the chain head is selected without serialization, and the chain is not exported to an independent retention boundary. Concurrent writes can branch from the same predecessor. Add a facility-scoped serialized chain head, database immutability and external append-only export/verification.
3. **Clinical governance and UAT remain mandatory.** Specialty templates, medication safety content, referral content, ICD-11/KHIS mappings, timed consultation usability and mobile workflows require named clinical owners and signed evidence.
4. **External integrations are readiness checks, not live services.** SHA, payment and patient messaging need secure sandbox certification, retry/reconciliation behavior and production monitoring.
5. **Production operations are not evidenced.** Complete restore drills, disaster recovery, observability/alerting, dependency patch policy, vulnerability remediation, DPIA, penetration testing and Kenyan digital-health certification evidence.

### P1 — next engineering work

1. Expand authenticated browser coverage through the full consultation, referral, pharmacy, payment and visit-closure journey; current coverage includes authentication, administration, access isolation, triage safety and mobile navigation.
2. Complete governed terminology approval and add the clinical medication-rule sources needed for interaction, dose, renal/hepatic, pregnancy, paediatric and severe-allergy checks.
3. Resolve or isolate the vulnerable `uuid` transitive dependency without the breaking automatic downgrade.
4. Add route-level error boundaries and production observability for client fetch failures and server exceptions.
5. Split the largest client workstations into workflow-focused modules to reduce review surface and support targeted interaction tests.

## Recommended next increment

Harden authentication first: enforce a 30-minute idle session timeout, add persistent failed-login throttling and audit successful/failed access events. Follow with a facility-scoped, serialized and database-immutable audit chain. These two increments reduce the largest engineering risk before expanding lower-priority clinical modules.
